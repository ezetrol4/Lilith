---

## 1. V1.1 Objective

Make an honest, evidence-backed claim about what Lilith covers in each OWASP Top 10:2025 category, and improve the categories where black-box testing can produce reliable, reproducible evidence.

V1.1 favors **accuracy, reproducibility, evidence quality and fewer false positives** over breadth. Adding more payloads, wider scanning or bigger coverage percentages is not a V1.1 goal.

V1.1 does **not** aim for "OWASP 10/10 coverage". Several 2025 categories (A06, A09, much of A03 and A08) can't be meaningfully assessed by a black-box scanner. Lilith will say so explicitly instead of implying coverage.

### Coverage-state vocabulary

| State | Meaning |
|---|---|
| `SUPPORTED` | Core attack surface of the category is tested with reliable, reproducible evidence and regression tests. |
| `PARTIAL` | A meaningful subset is tested with good evidence; significant sub-areas are missing. |
| `LIMITED` | A few peripheral or indicator-level checks exist; the core of the category is untested. |
| `MANUAL_REVIEW` | Lilith can only surface hints; a human must assess the category. |
| `NOT_ASSESSED` | Lilith produces no meaningful signal for this category. |

### Verification-type vocabulary

`EXTERNALLY OBSERVABLE` · `INFERABLE` · `AUTHENTICATED TEST REQUIRED` · `APPLICATION CONTEXT REQUIRED` · `SOURCE / SBOM CONTEXT REQUIRED` · `LOGGING / SIEM VISIBILITY REQUIRED` · `MANUAL DESIGN REVIEW REQUIRED`

| Concept | Current state | Gap |
|---|---|---|
| Unauthenticated vs authenticated behavior | Every scanner builds a fresh `requests.Session` with no credentials. The scan input is a URL only (`views._parse_target`). | No way to supply a session. Lilith can't see the authenticated surface or compare responses across auth states. |

## 3. Current Strengths

1. **A05 Injection.** Baseline-aware error detection (only *new* errors count), bounded reproducibility for timing and boolean evidence on form paths, conservative status semantics, and 56 deterministic tests.
2. **Reporting model.** `Severity` and `Confidence` are independent, `FindingStatus` separates `SECURE`/`INFORMATIONAL` from vulnerabilities, `summarize_findings` is the single counting authority, and severity ordering is stable.
3. **False-positive discipline in `cms.py` sensitive files.** Content markers are required for `CONFIRMED`, a non-HTML response without markers yields `MANUAL_REVIEW`, and an SPA HTML shell is suppressed. This is the model the other path-probe scanners should follow.
4. **Failure isolation.** One scanner's exception doesn't lose the others' results, and errors are sanitized.
5. **A02 breadth.** Headers, cookies, files, endpoints, DNS/email and ports give the widest externally observable coverage.
6. **Test suite.** No network, mocked timing, ~1.5 s run time, so changes get fast regression feedback.

### 6.5 Injection priorities (no new payloads)

1. CMD: restrict `CONFIRMED` to strong, structured markers (`root:x:0:0:`, a `uid=\d+\(\w+\) gid=\d+` regex, both `[fonts]` and `[extensions]`). Weak markers cap at `POTENTIAL`.
2. SQL/CMD time-based: add a **control** request (same payload shape with a zero delay) and require `delayed − control ≥ threshold` on both measurements. Measure the baseline against the *same action URL and method*.
3. SQL boolean: three-way comparison (true ≈ original, false ≠ original, repeat-consistent).
4. NoSQL: one bounded repeat for boolean and JSON-difference findings (consistent with SQL).
5. XSS: require an HTML `Content-Type` for reflected findings; re-detect the context at the payload's landing position; lower the header-vector severity for UA/XFF.
6. CMD/NoSQL URL-parameter bounded repeat (closes §61).
7. Extend SQL/CMD/NoSQL field discovery to `<textarea>`/`<select>`. This reaches existing fields; it adds no payloads.

### 8.2 Bounded malformed-input set (proposal — not implemented)

Each probe is sent at most twice (once, plus a repeat if it is anomalous), always compared with a **baseline** of the same endpoint and method with a benign value and with a **random-path 404 baseline**:

| Probe family | Example (single request, no fuzzing loop) | Observation |
|---|---|---|
| Malformed JSON | body `{"a":` with `Content-Type: application/json` on JSON-looking endpoints | 5xx vs 4xx; trace signatures |
| Type confusion | `param[]=x` where a scalar is expected; JSON `{"id": {"x": 1}}` | 5xx; exception class names |
| Invalid encoding | `%` / `%E0%A4%A` (truncated percent-encoding), lone surrogate in JSON | Decoder exceptions |
| Unexpected method | `PATCH` / unknown method on the target | Unhandled-method traces |
| Missing or incorrect `Content-Type` | POST form data labelled `application/json` | Parser exceptions |
| Oversized but bounded value | a single 8 KB parameter (no repetition, no flooding) | 413 vs 500 vs trace |
| Null byte | `%00` in one query value | Path/string handling exceptions |

Rules:
- `CONFIRMED` only for a trace/debug signature that is **new** relative to both baselines.
- A reproducible 5xx alone → LOW / `MANUAL_REVIEW` ("Unhandled exception condition"), never `CONFIRMED`.
- No resource-exhaustion, recursion-depth or decompression-bomb probes. Those are DoS-adjacent and out of scope.
- A hard per-scan request cap.

| Class | Definition |
|---|---|
| **SAFE TARGET** | Correctly secured implementation. Validates the absence of false positives. |
| **INTENTIONALLY VULNERABLE TARGET** | Known vulnerable implementation. Validates true positives. |
| **MISCONFIGURED TARGET** | Correct code, bad deployment configuration (headers, TLS, debug, files) |

### 8.4 Candidate targets

| Target | Strengths | Limits |
|---|---|---|
| **OWASP Juice Shop** | SPA catch-all (ideal soft-404 FP target); SQLi (login), NoSQL-style review endpoints, DOM XSS, BOLA (basket), error handling, misconfiguration | Node/Angular only. Many flows need JS execution; behavior changes between versions (pin the version). |
| **DVWA** | SQLi, blind SQLi, CMD injection, XSS (reflected/stored/DOM), brute force, CSRF. Security levels low → impossible give vulnerable and **safe** variants of the same endpoint. | Requires login plus a security-level cookie. That's an authenticated context Lilith can't supply today, so it's only usable via scanner-level harness tests. |

**Recommendation:** The LVT is the primary validation target for every P0 and most P1 items. DVWA (pinned) is secondary for injection true positives and false positives across security levels. Juice Shop (pinned) is secondary for SPA false positives and DOM behavior. WebGoat is manual study only.

### 8.5 Lab constraint: the SSRF guard blocks the lab

A lab on `127.0.0.1`, `192.168.x.x` or a Docker bridge network is rejected by `validate_url`. Once P0-1 enforces the guard on every request, scanners will reject it too. The lab **must not** be enabled by weakening the guard through settings, environment variables or request parameters. Instead, inject a lab-only network policy object **in code** from the validation harness, never from configuration a deployment could flip. This decision belongs in P0-1.

All lab validation runs on an isolated, operator-owned network. No external targets are contacted.

## 10. Regression-Test Requirements

Every V1.1 change must meet all of these:

1. **The existing 185 tests stay green.** An existing assertion may change only when its semantics are *intentionally* changed by a backlog item, and the PR must name the item (e.g. P0-5 updates the 5 `A03:2021` assertions).
2. **Test count never decreases.**
3. **No network and no real sleep.** All `requests`, `socket`, `ssl` and `dns` calls are mocked; time is mocked via `time.time`.
4. **Each check has at least one positive, one negative and one false-positive edge-case test.** The edge case must reproduce the specific heuristic weakness the change fixes (SPA shell, reflected keyword, slow-but-safe endpoint, "Welcome" on a failed login).
5. **Confidence and Status are asserted explicitly**, not just severity.
6. **Evidence assertions:** evidence contains the proof element (marker, timing, header) and contains **no** secret-like values. New scanners join `SensitiveDataLeakageTest`.
7. **Bounded request counts:** for any scanner that sends payloads, assert an upper bound on mock call counts so request volume regressions are caught.
8. **SSRF:** every new outbound code path gets a test proving it goes through the guarded session (after P0-1).
9. **Determinism:** three consecutive full-suite runs pass (as for V1).
10. **Mapping:** every finding carrying `owasp` uses a `:2025` constant from the central module (after P0-5).
11. **Lab validation is separate from the unit suite.** Lab runs are manual or opt-in, never part of `manage.py test`, and their results are recorded per backlog item: target, version, true positives, false positives.
